# Offline writes go through an Outbox queue, with ids the web picks

The web must work with no connection: the Feed, budget records, kanban, reminders and draw stay readable and writable offline, and what was written syncs once the connection is back. Before this, the service worker kept only the app shell; every `/api` request went to the network, so offline a page showed nothing and every write failed.

Seven decisions:

1. **Every write goes through the Outbox queue, online or not.** Creates, edits, archives, restores and deletes of notes (with their attachments and replies), expenses, incomes, boards, columns, cards, reminders and draw boards are written to an IndexedDB queue on the device first, and only then shown, marked **waiting to send**. The queue sends at once when online, and otherwise on the next app open with a connection, on the `online` event, or through Background Sync where the browser has it (Chrome on Android; Firefox and Safari do not). Offline is not a separate code path. One tab sends at a time (a Web Lock). Closing the tab, browser or phone loses nothing; a private window, clearing site data, or Safari's seven-day eviction of a site not added to the home screen does. The web asks for persistent storage (`navigator.storage.persist()`) the first time it queues.
2. **The web picks every new record's id.** Each create carries a UUID the web made when the owner made the record, so a resend after a lost reply cannot create a duplicate. Every downstream service validates it: an `id` that is not a UUID, or is the nil UUID, is **400**; an id the owner already holds returns that record (**200**, a resend); an id held by another owner is a plain **409** that reveals nothing about it. Every lookup is scoped to the minted identity's owner. The field is optional, so older clients and scripts keep working.
3. **The latest edit wins, field by field.** Each write carries the device time of each field's edit. The service stores a per-field edit time and applies an incoming field only where it is newer, so two devices that changed different fields of one record both keep their change; when they changed the same field, the later edit wins. Edit times later than the service's own clock are capped at its now, so a phone with a fast clock can't win forever. On a tie, the write that arrives last wins. Draw scenes are merged per element instead (see coredraw's ADR-0001); a draw board's doc text is one field.
4. **A permanent delete wins.** An edit to a record deleted elsewhere is dropped and shown in the Outbox queue as **deleted on another device**, with its content so the owner can copy it. A delete made offline applies when it syncs, whatever was edited in between. Archiving is a field like any other.
5. **Dependents wait; the rest keeps order.** An item waits for what it depends on (an expense before its note, a note's files before the note, a reply after the note it answers, a card after its column) and otherwise sends in the order it was made. An item the service refuses (400, 409, 413) stays in the queue as **couldn't send**, with the service's reason and Retry, Edit and Discard; items not depending on it keep sending. Network errors, 5xx (including corefinance's 502 when no exchange rate can be fetched) and 401 retry with backoff, forever; after a 401 the queue waits until the same account signs in again.
6. **Retention.** A confirmed item and its files leave the queue at once. Couldn't send and deleted on another device items stay until the owner acts on them; nothing is dropped on a timer. The last data each page loaded (**last-seen data**) is persisted per account, replaced whenever the page loads fresh, with no age limit; the Feed keeps the pages last scrolled, not its whole history. Signing out clears the queue and the last-seen data, after a warning if anything is still waiting; a release that changes the data's shape drops the last-seen data by bumping a cache version.
7. **What stays online-only.** Settings, API keys, export and import, admin pages and sign-in show "needs a connection" offline instead of queueing. Feed search offline covers only the notes saved on the device, and says so. Demo guests get the offline read view but no queue.

**Considered options**: queueing only while offline (rejected: two write paths, and the offline one is the rarely tested one); ids the service picks, matched up after sync (rejected: a resend after a lost reply duplicates the record, and links made offline, such as a reply to a waiting note, have nothing to point at); an `Idempotency-Key` header beside service-picked ids (rejected: the web still can't link to a record before it syncs); last write wins per record (rejected: a phone's offline rename and a laptop's due date change to the same card would lose one of them); refusing any edit to a record changed since it was loaded (rejected: one owner on several devices would spend their time resolving conflicts with themselves); `localStorage` or memory for the queue (rejected: memory dies with the tab, and `localStorage` is small and can't hold photos); creates only in the first version (rejected: the owner wants kanban and draw editable offline too).

**Consequences**: the gateway needs no change: it proxies the same requests, and the internal token is unchanged. Each service gains the `id` rules and per-field edit times (a migration per table that takes edits), deployable in any order, but the web turns on its queue for a service only once that service accepts ids, or a resend could duplicate. A note written offline is placed at the time it was written (`posted_at`, capped at now), not when it synced. A reminder made offline whose time passed before it synced is sent once on sync if the time passed less than 24 hours ago, and otherwise saved without sending (coreban's ADR-0007). A foreign-currency record made offline shows a peso estimate from the rates last saved on the device, marked "rate set when sent"; corefinance fixes the rate for the record's date when it syncs (corefinance's ADR-0003). Photos and videos are prepared on the phone (WebP, poster frames) when they are picked, offline too, and held in IndexedDB until they upload; they count toward the owner's quota only then. Couldn't send items need a page that lists the queue.
