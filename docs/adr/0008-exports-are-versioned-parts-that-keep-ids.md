# Exports are versioned parts that keep record ids

An export is a JSON bundle of **parts**, one per service (`budget`, `kanban`, `draw`, plus an export-only `account`). Each part has its own `format`, its own integer `version` and its own JSON Schema in the owning service's repo, and a part on its own is a valid file. The gateway serves the bundle (`GET /api/export`, `POST /api/import`) by calling each service's own part endpoints with the usual minted token; services never see the bundle. Import keeps every record's original id, so a record the caller already has is skipped. A file from another account is copied instead (see the amendment below). We chose this so parts can be imported separately, in any order and more than once, without breaking the links between services (a coreban note links a corefinance record by its id).

**Considered options**: new ids on every import, as the first budget import did (rejected: importing twice duplicates everything, and coreban's links to budget records point at ids that no longer exist); replace-on-import (rejected: one wrong file wipes a part); one version for the whole bundle (rejected: every service's change would bump everyone's format); the web app assembling the bundle (rejected: scripts using API keys would have to rebuild it, so the format would live in the UI rather than an endpoint); a single cross-service transaction (rejected: no distributed transaction for one user's data; because ids are kept, retrying a failed part is safe).

**Consequences**: a part's `data` uses export types of its own, never database rows, so a migration does not silently change the file format. `version` goes up only on breaking changes; an importer accepts its own version and older ones it can upgrade, and rejects newer ones. The unversioned budget export that came before is read as budget version 0. A part carries what the owner made plus the internal state that stops repeats (a rule's `materialized_through`, corefinance ADR-0001; a reminder's last occurrence, coreban ADR-0002); state that can be derived again (`next_due_at`, last-seen zones, delivery errors) is left out. Each part imports in its own transaction and reports its own result, so a bundle import can partly succeed. A link to a record not imported (yet) is kept and shows as missing. Device and credential data (notification targets, ntfy topics, API keys, sessions) and gateway admin data are never exported; attachment files are not either, only their metadata.

## Amendment (2026-11-27): a file can be imported into any account

The first version refused a file holding an id another user had, so a file could only go back into the account it came from, or into another once the first had deleted the data. An export now carries no account at all, and import works into any account:

- A part is **restored** when every id in it is free or already the caller's. The ids are kept, exactly as before.
- A part is **copied** when any id in it is held by another account, or when the caller already holds a derived id from an earlier copy. Every row then gets `uuidv5(namespace = caller's user id, name = the original id's 16 bytes)`, and so does every link: rule entries, tags, columns, labels, a reminder's card, a note's reply, card, reminder and budget record.

Every service derives ids the same way, and each repo has a test pinning one shared value. So a coreban note copied into an account still points at the corefinance record copied into it, in whichever order the parts are imported. Copying is deterministic, so importing the same file twice still changes nothing, even after the source account deletes its data. The file format is unchanged and stays at version 1.

**Consequences**: nothing is ever overwritten or deleted, in either account; import stays insert-only. A copied record has a new id, so links to the original (a board's URL, for one) don't open the copy. Each service decides restore or copy for its part alone, so links between parts match in both common cases: restoring into your own account, and copying into another one. They can miss only when the source account has deleted one service's data but not another's; a link that misses shows as missing, like any link to a record not imported. Attachment files stay with their account: a copied attachment is left out with a warning, because copying files on the strength of what a file claims would let a crafted file pull another user's photos. A failed import no longer reveals that an id exists in another account.

**Considered options**: new random ids on every copy (rejected: importing twice duplicates everything, and links between parts break); deriving ids per row instead of per part (rejected: the budget part can't see whether coreban kept or derived a note's id, so a restore into your own account could split links); an account id in the file to compare against (rejected: an export is meant to be portable and carry no account).

## Amendment (2026-11-28): snapshots name no account, and media travels in a zip

A round trip into a new account matched field for field except for two things, now fixed (#86):

- **Snapshots named the source account.** A linked note's snapshot was exported as stored: the trigger's view row (`owner_id`) or the corefinance record the web saved (`user_id`). Export and import now drop both keys, and a copy derives the row ids a snapshot holds (not a category's, which is the system's).
- **Photos and videos stayed behind.** A part carried attachment metadata only. A full export can now be a zip (`GET /api/export?media=true`): `export.json`, which is exactly the JSON export, plus `media/<attachment id>` and `media/<attachment id>.poster`, named by the ids in the file. The gateway streams each file from coreban (`GET /api/coreban/export/media/{id}`) into the zip. `POST /api/import` reads the zip front to back as it arrives, from its entries' local headers (`export.json` must come first), and sends the kanban part to coreban as multipart with each file it names as the zip reaches it. An entry ends at its header's size, at the end of its deflate stream, or (stored, with a data descriptor) at the size `export.json` gives that file; CRCs are checked. coreban works out every file's final id from the part, which comes first, then streams each file it needs straight into the bucket, before the import's transaction opens, so a long upload holds no transaction. It keeps a file already in the owner's storage (a restore), and checks each upload like one from the Feed. Nothing is written to disk on the way. The limit is the owner's attachment quota: an upload past it fails the part, and a request whose files add up to more than the quota is refused (413) as soon as it passes it. Admins have no quota. Uploads are queued for the attachment cleaner under a lease before they start, and the import's transaction takes them off the queue, so only a committed import keeps them. The format stays version 1; a JSON export without media is unchanged.

**Consequences**: an export with its media is complete; restoring or copying it brings everything back. An admin's export of another user never carries files, as the Feed never shows them their files. The gateway looks inside the kanban part to list its files, and nowhere else. A zip import over the owner's quota fails the kanban part. Long transfers extend their own read and write deadlines past the server's defaults, and nginx streams `/api/import` (with no cap of its own) and `/api/export`. The Data page downloads a zip through a hidden iframe, so the browser streams it to disk rather than holding it in memory.

**Considered options**: files base64-encoded inside the JSON (rejected: a third larger, and a few videos pass any sane JSON cap); copying files between accounts inside the bucket on import (rejected: a crafted file naming another user's attachment ids would copy their photos); a separate media endpoint the web calls file by file (rejected: an export should be one file a script can fetch with a key).
