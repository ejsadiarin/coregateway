# The gateway runs database backups, holding the owner credentials only for pg_dump

The gateway takes nightly and admin-triggered backups of the whole shared database (every service's schema) by running `pg_dump` against the owner connection (`MIGRATION_URL`), writing self-describing files to a backup folder outside the database. The owner connection string is passed only to the `pg_dump` subprocess; the gateway's Go code never opens a pool with it, and its own queries stay on the DML-only runtime role. This reverses the earlier rule that `MIGRATION_URL` stays on the laptop. We accepted that because a compromised gateway can already mint internal tokens with any user and any scope, so owner rights add little beyond DDL, and keeping it in the gateway matches how Immich runs backups in its own server with no extra service to deploy.

**Considered options**: a separate backup worker (keeps the gateway DML-only, but adds a service to build, deploy and proxy to); a Kubernetes CronJob (no app code, but a manual trigger then needs the gateway to hold RBAC to create Jobs, and compose has no equivalent); a table of backup records (rejected: the table lives inside the database it describes, so a restore elsewhere brings back rows for files that do not exist there).

**Consequences**: the backup folder is the only source of truth. File names carry the kind, UTC time and server major version; coordination between gateway replicas uses an exclusive lock file and the nightly file's existence on the shared volume, never the database. With more than one gateway replica the folder must be a shared (ReadWriteMany) volume. Restore is a documented manual `pg_restore`, never done by the app.
