# A user's timezone is owned by the gateway and asserted in the internal token

Downstream services that date things by "today" (corefinance rule entries, coreban reminders) need the user's timezone. The gateway stores it on the user, as an IANA zone, defaulting to UTC until the web saves the device's zone once. Each internal token carries the timezone of the user the request is about: the caller, or the target user in a targeted read. Background work that has no internal token (corefinance's worker, coreban's reminder dispatcher) looks it up from the gateway (superseded: see the amendment below). We rejected each downstream keeping its own copy, which is the situation today (coreban and corefinance each store one, and the web adopts the device zone twice): the copies drift and every new downstream repeats the work. We rejected a shared database view across schemas because it couples downstream schemas to the gateway's tables.

**Consequences**: a timezone change reaches requests when the next internal token is minted, within the token TTL. Downstream background jobs depend on the gateway's lookup and must fail closed (skip the pass and retry) rather than guess a zone, consistent with ADR-0002. The timezone claim becomes part of the shared internal token contract, so adding or renaming it ships in the gateway first.

## Amendment (2026-11-15): background work uses the last-seen zone

Background jobs no longer look a user's timezone up from the gateway. corefinance and coreban each keep the zone they last saw in a request's `tz` claim for that user, and their background work (corefinance's worker, coreban's reminder dispatcher) uses it. A token without `tz` means "use the last-seen zone", or UTC if the downstream has never seen one. `GET /api/users/{id}/timezone` is now the user's own only, like `PUT`; the admin-owned downstream-admin key path is gone.

We changed this to avoid deploy churn. The lookup needed an API key per background job (minted, stored and wired through env in every environment), a one-time copy of the downstreams' existing zones into the gateway, and a fixed deploy order between the gateway, the web and each downstream. With the last-seen zone none of that is needed, and the gateway, the web and the downstreams deploy in any order. The gateway still owns the timezone: the user saves it only there, and a downstream's kept zone is a copy of the claim, never set any other way.

**Trade-off**: a timezone change reaches a downstream's background work only on the user's next request to that downstream; until then its jobs date things in the previous zone. Requests themselves still see the change on the next mint. The "fail closed on a failed lookup" consequence above no longer applies to background jobs, since they make no lookup.
