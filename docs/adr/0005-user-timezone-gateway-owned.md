# A user's timezone is owned by the gateway and asserted in the internal token

Downstream services that date things by "today" (corefinance rule entries, coreban reminders) need the user's timezone. The gateway stores it on the user, as an IANA zone, defaulting to UTC until the web saves the device's zone once. Each internal token carries the timezone of the user the request is about: the caller, or the target user in a targeted read. Background work that has no internal token (corefinance's worker, coreban's reminder dispatcher) looks it up from the gateway. We rejected each downstream keeping its own copy, which is the situation today (coreban and corefinance each store one, and the web adopts the device zone twice): the copies drift and every new downstream repeats the work. We rejected a shared database view across schemas because it couples downstream schemas to the gateway's tables.

**Consequences**: a timezone change reaches requests when the next internal token is minted, within the token TTL. Downstream background jobs depend on the gateway's lookup and must fail closed (skip the pass and retry) rather than guess a zone, consistent with ADR-0002. The timezone claim becomes part of the shared internal token contract, so adding or renaming it ships in the gateway first.
